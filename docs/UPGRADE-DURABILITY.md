# Durability подготовленного дерева upgrade

Исследовано на HEAD a62ad73dcd3726ef94c8720712b8738747ebe7d6. Потеря
подготовленных каталогов после отключения питания не воспроизведена;
подозрение не считается пятым подтверждённым дефектом. Завершение процесса
через SIGKILL/os._exit оставляет ядро, page cache и файловую систему работающими.
Оно проверяет восстановление процесса, но не моделирует потерю питания.

`atomic()` уже делает fsync нового файла и его непосредственного родителя.
`sync_rename()` синхронизирует обе стороны переименования. Однако создание
`package/`, `backups/`, `code/bin` и hard links бинарников не завершалось явной
синхронизацией всех новых записей каталогов до публикации `prepared`.
Синхронизация файла не гарантирует сохранение его имени в каталоге;
[Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) требует
отдельной синхронизации каталога. Поэтому вывод о сохранности всего дерева
не следует только из успешного fsync журнала.

Исправление оправдано как обеспечение требуемого порядка записи, без утверждения
о воспроизведённой потере. До `prepared` выполняется синхронизация всех обычных
файлов подготовленной транзакции (включая inode hard links бинарников), затем
каталогов снизу вверх, корня транзакции и его родителя. Таким же способом
синхронизируется подготовленное поколение и каталог `generations/`. Ошибка
синхронизации прерывает подготовку до изменения живого комплекта. Отдельно
синхронизируются независимый recovery engine, новые юниты/drop-in, публикация
устойчивой преграды и удаление файлов при откате.

Регрессионная файловая проверка подтверждает, что package, backups, code/bin,
code, transaction и поколение синхронизированы перед prepared. Linux-прогоны
действительно исполняют fsync на контейнерной ФС и проверяют аварии процесса,
SIGTERM и ошибки публикации. Ни одна из этих проверок не подтверждает порядок
записи при потере питания конкретного накопителя/гипервизора.

Остаётся непроверенной фактическая устойчивость при отключении питания для
конкретной ФС, режима журналирования, storage cache и виртуализации. Для такого
подтверждения нужен отдельный одноразовый блочный образ с управляемыми сбоями
записи/перезапуском ФС и проверкой восстановленного дерева. Рабочий VPS для
исследования не использовался.

Дополнение повторного ревью: прежний worker с открытым до upgrade дескриптором
успешно обходил symlink-преграду после гибели владельца flock. Исправление
сохраняет то же открытое файловое описание у systemd/PID 1 до завершения файлового
отката; guardian получает его при перезапуске. Перед prepared подтверждается
приём FDSTORE через BARRIER. Активный hold target удерживает юнит от выгрузки.
При перезапуске PID 1 дескрипторы и прежние процессы исчезают; boot recovery
использует сохранённую symlink-преграду и journal. Это отдельный механизм
восстановления, без обещания сохранения flock на диске при отключении питания.

Переключение recovery-инфраструктуры проверяется при гибели процесса после каждой
публикации. До изменения recovery-юнита доступны совместимый loader, полный
checksum-движок и юнит завершения служб. Устаревший cached ExecStart через
recover.py поддерживается отдельно. Эти проверки и повторная загрузка контейнера
не подтверждают поведение ФС при потере питания.

Третье ревью воспроизвело потерю процесса после успешного `activate()` до commit
upgrade на настоящем установленном a62ad73: backend.yaml восстановлен, но PID
Mihomo оставался прежним и загрузка старых providers возвращала
`PROVIDERS_NOT_READY`, несмотря на `services_restored: true`.
Guardian теперь использует режим отложенной остановки; cold-boot recovery
по-прежнему не останавливает ожидающие start jobs. После завершения boot guard
отдельная finish-служба перезапускает core без policy lock и проверяет
восстановленное поколение, загруженные providers, DNS TCP/UDP и REJECT.
Преграда снимается guardian до освобождения исходного flock; FDSTORE удаляется
после завершения защищённых файловых операций. Старое terminal-состояние без
доказательства проверки служб требует повторной проверки, без повторного
восстановления файлов. Инъекции потери процесса и данные прогонов сохранены
в `verification/head-review-fixes.json`; ограничения по потере питания прежние.
