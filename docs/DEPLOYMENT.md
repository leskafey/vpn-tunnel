# Установка и обслуживание

Справочник по обслуживанию и нестандартной установке
[vpn-tunnel](https://github.com/leskafey/vpn-tunnel).
Серверные команды выполняются **от root** на Ubuntu 24.04 x86_64 в Bash/zsh.
Требования, основной сценарий установки, создание устройства и подключение
описаны в [README](../README.md). Локальные проверки кода и исторические
отчёты — в [DEVELOPMENT](DEVELOPMENT.md).

## Каталог установки

Рекомендуемый каталог — `/root/vpn-tunnel`. Установка использует каталог,
где находится `install-vpn.py`, независимо от текущего рабочего каталога.
Корень проекта должен принадлежать root и не быть доступен для записи
другим пользователям. `/root` и сам проект могут иметь закрытые права `0700`:
доступ служб обеспечивается отдельным пространством файлов systemd.
Права исходных родительских каталогов установщик не меняет.

Пробелы, кавычки, обратная косая черта, `$` и UTF-8 в пути поддерживаются.
Недопустимы `%`, перевод строки и возврат каретки. Полный абсолютный путь
корня проекта — не более **73 байт в UTF-8**. Ограничение связано с постоянным
Unix-сокетом `cache/backend/controller.sock`: его полный путь должен занимать
менее 104 байт, чтобы осталось место для завершающего NUL.
Путь проверяется до создания состояния установки и загрузки бинарников;
ошибка длины — `PROJECT_UNIX_SOCKET_PATH_TOO_LONG`. Выберите более короткий
каталог до первой установки. Пример допустимого пути:
`/srv/deployments/vpn-projects/vpn-tunel`.

Не перемещайте установленный проект: службы и сохранённые политики содержат
его абсолютный путь.

### Доступ DNS и HTTP к закрытому каталогу

DNS и HTTP продолжают работать от `vpn-policy`, с `ProtectSystem=strict`.
Для `/root/vpn-tunnel` в пространстве каждой службы создаются пустые tmpfs
только для чтения вместо `/root`, `/home`, `/run/user` и корня проекта.
Если есть другие закрытые родители, временные каталоги покрывают всю нужную
цепочку. Это отдельное представление файлов: настоящие права `/root` не
меняются, ACL для него не добавляются.

`BindReadOnlyPaths` подключает `lib/` и `data/` по прежним абсолютным путям.
DNS дополнительно видит `config/` и получает запись в `cache/backend/` через
`BindPaths` и `ReadWritePaths`. HTTP не получает доступа к конфигурациям и кэшу.
Подключаются каталоги, поэтому атомарная замена `backend.yaml` и публикация
новых поколений видны службам. `profiles/` и `state/` не подключаются;
ключи, реестр устройств и исходные личные правила в `config/` остаются `0600`.

В DNS/HTTP-юнитах `ProtectHome=no` сочетается с явными tmpfs для домашних
каталогов. Встроенные режимы `ProtectHome` перекрывают монтирование `/root`,
а `ProtectHome=tmpfs` задаёт ему `0700`, что препятствует проходу `vpn-policy`.
Защиту здесь обеспечивают явные временные каталоги и разрешённые bind-монтирования.
Корневые службы обновления сохраняют `ProtectHome=read-only` и свои точечные
`ReadWritePaths`; их доступ к приватным данным нужен для обслуживания.

Для путей с кавычками, обратной косой чертой, двоеточием или табуляцией
сохраняется обычная модель доступа по правам пользователя: в systemd 255
такие bind/tmpfs-пути могут изменяться при передаче исполняющему процессу.
В этом случае корень и родители должны разрешать проход `vpn-policy`.
Аудит проверяет фактический проход от существующего пользователя, включая
его группы и уже заданные ACL. Если пользователя ещё нет, нужен проход для
остальных пользователей, как в прежнем сценарии. Установщик не добавляет ACL
и не открывает закрытые родители для таких нестандартных путей.
Используйте рекомендованный путь без этих символов для установки под закрытым `/root`.

Аудит проверяет модель доступа, поддержку пространств монтирования и tmpfs,
а также `CAP_SYS_ADMIN` процесса установки. Он не меняет права, не создаёт
пользователей и не изменяет службы. Дополнительные пакеты для механизма доступа
не нужны; эти требования относятся и к установке одним `install-vpn.py`.
При установке и `--resume` служебные каталоги получают нужных владельцев,
группы и права перед запуском служб. Права проекта и его родителей сохраняются.
`vpn-policy` должен иметь отдельные ненулевые UID и GID.

### Служебные каталоги и права

Все пути в таблице указаны относительно корня проекта:

| Путь | Содержимое |
| --- | --- |
| `lib/`, `lib/bin/` | Установленный код, четыре базовых `*hosts.txt`, четыре базовых `*ips.txt` и закреплённые бинарники |
| `config/` | Личные правила, настройки, конфигурации Xray и DNS, реестр устройств и приватные данные доступа |
| `profiles/` | Пользовательские SMART/FULL-профили; каталог `0700`, JSON `0600` |
| `data/generations/`, `data/current` | Проверенные серверные политики и небольшие клиентские JSON; `current` ссылается на активное поколение |
| `data/` | Блокировка обновлений и журналы восстановления |
| `cache/backend/` | Рабочий кэш Mihomo; владелец `vpn-policy`, права `0700` |
| `state/install/` | Журнал установки, контрольная точка ключей и временные загрузки |
| `state/upgrade/` | Приватный журнал обновления, независимый загрузчик восстановления и резервные копии заменяемого кода/конфигураций |

Приватные конфигурации root имеют `0600`; необходимые DNS/HTTP файлы доступны
только root и группе `vpn-policy` (`0640`, каталоги `0750`). Личные правила и
профили не доступны HTTP-службе. Установленный код, конфигурации, профили,
ключи, кэш и рабочие данные исключены из Git.
Команда `/usr/local/sbin/vpnctl` и юниты `/etc/systemd/system/vpn-stack-*`
находятся в системных каталогах. Отдельного корня рабочих данных вне проекта нет.
DNS, SOCKS и HTTP правил слушают loopback.

Проверка политики использует короткий приватный временный сокет
`data/.s-XXXXXXXX/api.sock`, а её конфигурации и MRS остаются в поколении.
Каталог сокета имеет `0700` и удаляется после остановки проверочного процесса,
включая ошибки проверки.

## Установка без Git

В этом варианте Git не нужен; остальные [требования README](../README.md#требования)
сохраняются. Скопируйте один `install-vpn.py` в корень будущей установки,
например `/root/vpn-tunnel/`, с владельцем root и правами каталога `0700`
или `0755`.
Бинарники скачиваются отдельно и проверяются по закреплённым SHA-256.
Не запускайте файл из `/tmp` или чужого доступного для записи каталога.

```sh
python3 /root/vpn-tunnel/install-vpn.py audit
systemd-run --wait --pipe --collect --unit=vpn-stack-install \
  -p MemoryMax=768M -p MemorySwapMax=0 -p TasksMax=64 \
  -p RuntimeMaxSec=1800 -p UMask=0077 \
  /usr/bin/python3 /root/vpn-tunnel/install-vpn.py install --server-ip IP_НОВОГО_VPS
```

Укажите публичный IPv4 VPS вместо `IP_НОВОГО_VPS`. Эта команда задаёт те же
лимиты процесса установки, что и `install.sh`. Признак успеха —
`VPN_STACK_INSTALL_OK`. Установщик не меняет firewall; входящий TCP 443
должен быть открыт.
Итоговый отчёт показывает каталог профилей и полные пути файлов личных правил.

## Восстановление прерванной установки

Установка рассчитана на чистый VPS, в том числе после переустановки ОС.
Повторный запуск не перезаписывает существующую установку. После прерывания
устраните причину и добавьте `--resume` к исходной команде установки.
Сохраните версию установщика, каталог и публичный IP. Для `install.sh`
команда приведена в [README](../README.md#установка-на-vps); при установке
без Git добавьте `--resume` после IP в команде `systemd-run` выше.

Ключи и служебный UUID берутся из контрольной точки
`state/install/identity.json`; личные правила сохраняются без перезаписи.
Начальных пользовательских устройств нет. SMART/FULL для проверки создаются
временно и удаляются. Служебная учётная запись `probe` не выдаётся пользователю:
она остаётся в серверных конфигурациях и приватной конфигурации проверок.

Журнал `state/install/installation.json` хранит статус установки, IP и
контрольные суммы кода, бинарников, юнитов и приватных конфигураций. При
продолжении установщик сверяет сохранённое состояние и отказывается принимать
несовпадающий код или изменённые управляемые файлы. Личные правила сохраняются
отдельно и не требуют возврата к исходному содержимому.

Начальный журнал готовится в приватном временном каталоге
`.vpn-initialize-*/state/install/` внутри проекта. После записи и синхронизации
контрольной точки весь `state/` публикуется атомарно, без замены существующего
каталога. Прерывание до публикации не оставляет штатного `state/` без журнала:
`--resume` заново проходит проверки чистого сервера и начинает инициализацию.
Если публикация завершена, используется готовый журнал.

После аварийного завершения временный каталог подготовки может остаться.
Установщик не принимает его за состояние и не переносит из него файлы.
Чужие каталоги, приватные конфигурации или штатное состояние без журнала
не удаляются и не принимаются за собственную установку. Отсутствие журнала
при уже созданной идентичности приводит к отказу; существующие ключи и UUID
сохраняются.

## Обслуживание устройств

[Повседневные команды](../README.md#управление-устройствами) описаны в README.
Имя устройства — от 1 до 40 символов: первая буква `a`–`z`, далее строчные
латинские буквы, цифры или дефис. Имя `probe` зарезервировано.
Поддерживается до 256 пользовательских устройств.

`list` показывает только имена пользовательских устройств. Служебная учётная
запись проверок скрыта из списка и не имеет файлов в `profiles/`.
`export` выводит пути и восстанавливает отсутствующие JSON с прежним UUID.
Каталог `profiles/` должен существовать, принадлежать root, быть приватным
и не быть симлинком. Изменённые вручную JSON не перезаписываются: возвращается ошибка.

`revoke` отзывает доступ и локально проверяет отказ. Отсутствие каталога
профилей не препятствует отзыву. Неизменённые JSON удаляются, изменённые
сохраняются с сообщением; их UUID уже отозван.

Добавление и отзыв перезапускают Xray, соединения могут переподключиться.
Журнал `data/device-transaction.json` содержит данные для возврата конфигурации
Xray, реестра устройств и затронутых профилей. Незавершённая операция
откатывается перед следующей операцией с устройством или запуском Xray после
перезагрузки. После отката незавершённого отзыва повторите `revoke`.

## Правила и лимиты

Назначение файлов, команды и приоритеты правил описаны в
[README](../README.md#личные-правила).

Доменные файлы — UTF-8, одна запись на строку, без схемы, порта и пути.
Запись охватывает домен и поддомены, `#` начинает комментарий.
Общий предел каждого доменного файла — 64 КиБ, строки — 4096 байт;
PROXY, ads и ads-exceptions — до 2048 уникальных доменов.
Личный DIRECT — до 256 доменов и 32 КиБ клиентского JSON.

Личные IP: UTF-8-комментарии, активные записи ASCII; публичные IPv4/CIDR,
маски `/12`–`/32`, у сетей нулевые биты хоста. Парсер Python `ipaddress`
проверяет `is_global` сети, первого и последнего адреса, отдельно запрещает
multicast. Это проверка свойств адресов, а не доступности или владельца сети.
До 256 входных записей до удаления дублей и 32 КиБ файла вместе с комментариями.
Итог вместе с автоматическими IP — до 256 свёрнутых CIDR и 32 КиБ JSON.
Удаление личного IP не удаляет такое же автоматическое правило.

Большие источники для личных правок заново не скачиваются. Невалидная правка
сохраняет рабочую политику. Задержки применения и интервалы доставки SMART
указаны в [README](../README.md#личные-правила) и
[разделе обновлений](../README.md#обновления-и-обслуживание).
На отключённом устройстве обновление возможно после подключения.
FULL клиентские списки IP и DIRECT не загружает.

## Обновление установленного кода

`./install.sh upgrade` или `python3 install-vpn.py upgrade` запускаются от root
из прежнего каталога проекта. Нужна завершённая установка, рабочие DNS/HTTP/Xray
и завершённое восстановление устройств. Сохраняются адрес VPS, ключи, UUID,
реестр устройств, клиентские JSON, существующие личные правила и кэш Mihomo.
Отсутствующие новые файлы правил создаются с закомментированными примерами;
при неудачном обновлении они могут остаться как пустые по смыслу личные списки.

Базовые доменные, рекламные и IP-списки устанавливаются в `lib/`, отдельно от
личных `config/*.txt`. Их изменения входят в пакет `install-vpn.py` и
доставляются через `upgrade`: подготовленный комплект проверяется до
переключения, а при откате восстанавливается весь прежний `lib/` вместе
со списками. Отсутствие обязательного файла или несовпадение SHA-256
завершает установку/обновление ошибкой; неполная политика не применяется.
При `upgrade` автоматические IP собираются заново из официальных источников
и локальных файлов целевого пакета, затем объединяются с личным `config/proxy-ip.txt`.
Проверки покрытия, размеров и клиентской политики выполняются до переключения.
Поэтому изменение только базового IP-файла также применяется через `upgrade`.

Обновление проверяет контрольные суммы установленного кода, базовых списков,
бинарников, CLI и юнитов по журналу установки. Ссылки вместо `lib/`/`bin/` и неизвестные юниты,
занимающие новые управляемые имена, отклоняются. Смена закреплённых версий
Xray/sing-box/Mihomo этим режимом не поддерживается: она завершается отказом
до переключения. Требования к ОС, архитектуре и диску прежние.
Для `upgrade` требуется минимум 512 МиБ доступной RAM (`MemAvailable` в
`/proc/meminfo`); первоначальная установка и её продолжение требуют 650 МиБ.
Это проверка доступной памяти перед подготовкой, а не лимит процесса обновления.

Порядок обновления:

1. Захватить блокировки установки и политики, подготовить отдельный комплект кода
   и проверить новую политику на полных MRS и изолированном DNS.
2. Передать тот же открытый дескриптор policy lock guardian и дождаться
   подтверждения хранения у systemd/PID 1. Синхронизировать дерево и резервные копии, установить устойчивую
   преграду для старых и новых workers и CLI, сохранить `prepared`; остановить
   таймеры/watcher и службы VPN.
3. Переместить прежний `lib/` в резервную копию и установить подготовленный каталог,
   обновить юниты и CLI, дождаться загрузки старой политики и готовности DNS.
4. Активировать новую политику с транспортными проверками, обновить журнал установки
   и зафиксировать выбор версии с `services_restored: false`. Освободить policy lock,
   восстановить службы, проверить загруженные providers и DNS TCP/UDP относительно
   поколения, проверить REJECT и включить прежние таймеры/watcher.
   Только после успеха записать `services_restored: true`.

Ключи и профили не пересоздаются. У VPN есть короткий перерыв при переключении
служб; длительная загрузка и компиляция списков выполняется до этого перерыва.
Проверка готовности DNS выполняется дополнительно к `systemctl start`.

`state/upgrade/transaction.json` содержит состояния `prepared`, `applying`,
`rolling_back`, `rolled_back`, `committed` (схема 1 сохраняется). Поле
`services_restored` отдельно отмечает завершение восстановления служб. Старые
журналы без этого поля или без `service_verification` требуют повторной проверки служб, без
повторного отката файлов из terminal-состояния. Транзакция хранится в приватном
`state/upgrade/up-<id>/`: `package/` для восстановления, `backups/` для файлов,
`old-lib/` для прежнего комплекта кода. Резервные копии сохраняются после успеха;
`vpnctl cleanup` их не удаляет. Не удаляйте их при незавершённой транзакции.

Служба `vpn-stack-upgrade-recover.service` запускает
версионированный `state/upgrade/recover-v2.py`, не зависящий от наличия живого `lib/`. Управляемые
службы, таймеры и watcher получают прежний drop-in с `Requires`/`After` этой службы.
Движок сохраняется в приватном `engine-<sha256>/` с проверяемым manifest;
`engine.json` публикует выбор движка атомарно. Он доступен при отсутствующем
`lib/` и поддерживает прежние журналы и поколения. Миграция принимает только
точные байты загрузчика и юнитов a62ad73, предыдущих исправлений ревью либо текущей версии.
Сначала проверяется существующая инфраструктура, подготавливается и проверяется
полный новый движок. Затем публикуются и синхронизируются оба совместимых
загрузчика — `recover-v2.py` и `recover.py` для прежнего ExecStart, в том числе
закешированного systemd. Только после этого переключается `engine.json`,
обновляются юниты завершения/recovery/guardian и drop-in, выполняется daemon-reload.
До переключения новые загрузчики работают с прежними движками: Python-only
и пакетом шага 2 с четырьмя доменными/рекламными файлами; после переключения
оба принимают новый пакет с восемью базовыми списками. Точные загрузчики
шага 2 также принимаются для миграции.
При первом создании engine для исходного legacy-загрузчика без указателя
полный engine выбирается заранее: прежний загрузчик игнорирует этот указатель
и продолжает читать пакет транзакции, а новый уже может открыть выбранный engine.
Загрузчик, использующий engine, при отсутствии указателя отклоняется.
Старый пакет транзакции сохраняется целиком.
Изменённая пользователем инфраструктура не перезаписывается.
При загрузке она откатывает незавершённое обновление до старта зависимых служб.
Откат восстанавливает код, юниты, CLI, журнал установки, конфигурацию DNS и указатель
активной политики. Контрольные суммы резервных копий проверяются; ручная правка
заменяемого файла во время сбоя останавливает восстановление, сохраняя эту правку.

До фиксации выбора версии `data/update.lock` атомарно заменяется ссылкой на
приватный каталог; оба прежних runtime отказываются работать с таким lock.
Исходный inode сохраняется hard link в `state/upgrade/policy.lock`, который
использует recovery. Одной ссылки недостаточно для прежних процессов, уже
открывших исходный inode: их останавливает flock на том же открытом файловом
описании, переданном через SCM_RIGHTS guardian и в FDSTORE systemd/PID 1.
`prepared` публикуется только после BARRIER и проверки принятого дескриптора.
Новый runtime
также проверяет журнал под lock; прямой cleanup отказывается удалять поколения
незавершённого upgrade. Не исправляйте ссылку вручную: выполните recovery.
После восстановления файлов guardian снимает преграду ещё под исходным flock,
затем освобождает lock и FDSTORE. Cold-boot guard снимает преграду до своего
завершения, чтобы восстановление устройств могло получить lock.

`vpn-stack-upgrade-guardian.service` получает этот дескриптор при перезапуске
и восстанавливает файлы после освобождения install lock основным процессом.
Он использует переданный flock без повторного захвата через другой open.
`vpn-stack-upgrade-hold.target` удерживает ссылку на юнит; FDSTORE с
`FileDescriptorStorePreserve=yes` сохраняется даже при остановке самого guardian.
При ошибке отката блокировка остаётся у PID 1, guardian повторяет попытку;
`upgrade --recover` также перезапускает guardian и ждёт его вне install lock.
Разблокировка и удаление FDSTORE разрешены после окончания файловой транзакции.
Службы запускаются отдельно после освобождения policy lock.
Нужен systemd **254 или новее**; неподдерживаемый FDSTORE вызывает отказ до
публикации `prepared`. Ubuntu 24.04 использует systemd 255.
Протокол описан в [systemd.service](https://www.freedesktop.org/software/systemd/man/systemd.service.html)
и [sd_notify](https://www.freedesktop.org/software/systemd/man/sd_notify.html).

Служба `vpn-stack-upgrade-services.service` с `After` recovery guard завершает
запуск служб после его выхода. При `rolled_back` она останавливает triggers/workers
и выполняет настоящий `restart` DNS/HTTP/Xray, даже если они уже активны.
Это загружает восстановленный `backend.yaml` и код; `start` активного Mihomo
этого не делает. При потере процесса этот перезапуск повторяется безопасно.
Перед перезапуском сбрасывается failed-состояние и счётчик стартов именно
восстанавливаемых core-служб: серия аварий recovery иначе может оставить
Mihomo в `start-limit-hit` даже с уже восстановленной конфигурацией.
Проверяются контрольные суммы конфигурации и файлов поколения, полный состав и
counts providers через Unix API, DNS TCP/UDP для трёх публичных controls и
трёх свидетелей поколения, а также REJECT рекламного fake-IP. Снимок личных
правил берётся из поколения, новые пользовательские правки не перезаписываются.
Counts используются вместе с перезапуском из проверенной конфигурации и
проверкой поведения: одинаковые counts сами по себе не доказывают совпадение
правил. Проверочные helpers читаются из recovery engine, поэтому старый `lib/`
может не содержать новых модулей. Только после успешных проверок сохраняются
`service_verification` и
`services_restored: true`. Она не имеет обратной зависимости guard от себя;
guard ставит её запуск в очередь без ожидания. Сам guard имеет
`DefaultDependencies=no`, ждёт локальную ФС и mount проекта, поэтому не
образует цикл `guard → basic.target → paths.target → watcher → guard`.
При откате прежнего журнала сохраняется только точная проверенная миграция recovery-юнита
и юнита завершения служб;
оригинальная резервная копия не меняется. Старая контрольная сумма этого
точного юнита в installation.json принимается при следующем upgrade только
в сочетании с точными байтами нового recovery-юнита. Ошибка запуска или потеря
процесса оставляет `false`; повторный `upgrade --recover` продолжает запуск,
сохраняя уже восстановленные файлы и пользовательские изменения после отката.

У работающего сервера guardian выполняет файловый откат с отложенным перезапуском;
это отдельный режим от cold-boot recovery, где прежние процессы уже исчезли.
Guardian может быть нужен boot guard, пока start jobs DNS/Xray ждут завершения
того же guard. Поэтому синхронный `stop` этих служб внутри guardian способен
отменить ожидающие jobs; остановка и перезапуск выполняются только в finish-фазе
после guard. Зависимые workers и восстановление устройств запускаются без
удержания policy lock. При обычном ручном откате core можно остановить до
восстановления файлов; finish-фаза всё равно проверяет загруженную политику.

`upgrade --recover` выполняет только восстановление, без требований к свободной
памяти/диску для новой сборки. Обычный `upgrade` при обнаружении незавершённой
транзакции тоже сначала откатывает её и возвращает `status: recovered`;
для новой попытки обновления запустите команду повторно. После успешной фиксации
эта команда не отменяет уже завершённое обновление.

`vpnctl status` показывает состояние обновления и отмечает незавершённый журнал
как неисправность, включая `services_restored: false`. Состояние `rolled_back`
означает завершённое восстановление файлов; полный recovery завершён только
при `services_restored: true`. Здоровье DNS/HTTP/Xray проверяется отдельно
в том же статусе.

## Источники и обновления

Домены: [rulist](https://github.com/bol-van/rulist),
[antifilter](https://antifilter.download/list/domains.lst),
локальные `include-hosts.txt`/`exclude-hosts.txt` из `lists/baseline/`,
[oisd small](https://github.com/sjhgvr/oisd).
Реклама объединяется из OISD small,
[AdGuard DNS Filter](https://github.com/AdguardTeam/AdGuardSDNSFilter)
и локального `include-adblock-hosts.txt`. Исключения берутся из AdGuard и
локального `exclude-adblock-hosts.txt`. Четыре дополнения читаются из
установленного `lib/` без запросов к AntiZapret. Проверка делегированных TLD
по IANA сохраняется.

Обычные рекламные правила, исключения источников и поддерживаемые
`$important` хранятся раздельно в MRS; точные исключения сохраняют точное
совпадение. Личные правила остаются inline. Приоритеты — в
[README](../README.md#личные-правила).

Метаданные `source_metadata` в манифесте поколения содержат размеры, SHA-256,
число входных правил, обработанных блокировок/исключений и неподдерживаемых
конструкций. AdGuard: 10 000–1 000 000 входных правил, не более 5% неподдерживаемых
(минимальный допуск — 10 строк). Базовые рекламные списки: 0–10 000 правил;
пустой список с комментариями допустим. Для новых источников после первой загрузки изменение
числа правил ограничено 25% (минимальный допуск — 10 строк).
Локальный reader ограничен 256 КиБ на файл: наибольший подготовленный
вход занимает 18 116 байт, а данные теперь входят в пакет с общим пределом
1 МиБ. Это дополнительный предел для встроенных данных; прежние ограничения
числа рекламных правил и формата сохраняются.
Локальные входы имеют `source: local-baseline`, путь, размер и SHA-256;
доменный `commit` больше не требуется. Исторические ключи
`antizapret-ads`/`antizapret-ads-allow` сохранены для сравнения числа записей
с прежними поколениями: они теперь обозначают локальные входы. Повторное
использование поколений поддерживает как прежний `commit`, так и его отсутствие.
Прежние ограничения размеров/числа записей, изменения на 25% и запрет
потери доменного покрытия сохранены.
Ошибка чтения, загрузки, разбора, MRS или проверки сохраняет активное поколение.

IP Telegram: [официальный CIDR](https://core.telegram.org/resources/cidr.txt)
плюс локальный `telegram-extra-ips.txt`; Cloudflare:
[официальный IPv4](https://www.cloudflare.com/ips-v4/) плюс `cloudflare-extra-ips.txt`.
Discord и WhatsApp: локальные `discord-ips.txt` и `whatsapp-ips.txt`.
Все четыре файла читаются из установленного `lib/`, отдельно от личного
`config/proxy-ip.txt`. Состав дополнений и происхождение сохранены в
[PROVENANCE.json](../lists/baseline/PROVENANCE.json); загрузок из AntiZapret-VPN нет.

Каждый IP-вход ограничен 16 КиБ, содержит 1–256 уникальных публичных IPv4 CIDR
с префиксом не шире `/12`. Telegram дополнительно ограничен 7–12 IPv4 CIDR
не шире `/20` и максимум 16 IPv6 CIDR не шире `/32`; IPv6 проверяются и
не доставляются клиентам. Cloudflare допускает 10–32 IPv4 CIDR, IPv6 отклоняются.
Пустые списки, повторные CIDR и некорректные активные записи отклоняются; совпадающие
диапазоны разных источников и вложенные сети сворачиваются по покрытию.
Автоматическое покрытие не может терять прежние адреса или вырасти более чем
на 25%. Личные IP объединяются с автоматическими после этой проверки.
Итоговый клиентский JSON ограничен 256 CIDR и 32 КиБ. Ошибка любого
обязательного официального или локального источника сохраняет всю рабочую
политику; без рабочей политики установка завершается явной ошибкой.
Метаданные IP содержат URL/путь, размеры, SHA-256 и количество CIDR входов
в `ip.sources`; `source_CIDRs` остаётся автоматическим покрытием без личных
правил. Прежние IP-метаданные с `commit` поддерживаются при повторном
использовании поколений и восстановлении; новая сборка IP этого поля не создаёт.
Расписание и поведение при ошибках — в [README](../README.md#обновления-и-обслуживание).

Закреплённые компоненты: [Xray 26.3.27](https://github.com/XTLS/Xray-core/releases/tag/v26.3.27),
[sing-box 1.14.2](https://github.com/SagerNet/sing-box/releases/tag/v1.14.2),
[Mihomo 1.19.31](https://github.com/MetaCubeX/mihomo/releases/tag/v1.19.31).
[Компоненты и источники](../NOTICE.md).

Для ручного запуска обновлений:

```sh
systemctl start vpn-stack-daily.service
systemctl start vpn-stack-ip.service
```

Первый сервис обновляет доменные источники, второй — IP-источники.
Оба используют уже установленные локальные дополнения. Эти задания не
получают новые версии `lists/baseline/` из Git: для доставки изменений общих
списков нужен новый установщик и `upgrade`. Личные правила меняйте через
`vpnctl rule` или `config/*.txt`; файлы в `lib/` вручную не редактируйте.
Порядок изменения общих списков описан в
[руководстве по разработке](DEVELOPMENT.md#сопровождение-собственных-списков).

## Диагностика и очистка

```sh
vpnctl status
vpnctl cleanup
journalctl -u vpn-stack-personal.service -n 30 --no-pager -o cat
journalctl -u vpn-stack-daily.service -n 60 --no-pager -o cat
journalctl -u vpn-stack-ip.service -n 60 --no-pager -o cat
```

Статус проверяет локальные Xray/DNS/HTTP, systemd-службы и таймеры,
целостность сохранённых конфигураций, незавершённые транзакции и неприменённые
личные правки. Наличие неприменённых правок отражается в отчёте и само по себе
не означает ненулевой код. Успешный неактивный oneshot нормален; штатный
отложенный запуск с кодом 75 не ухудшает статус. OOM, сигнал, тайм-аут и другие
ошибки служб дают `degraded` и код 1. Внешний вход, интернет и подключение
физического устройства проверяются отдельно.

Журнал `data/transaction.json` хранит состояние применения политики и данные
для отката. Следующий запуск обновления восстанавливает незавершённую
транзакцию. Не удаляйте журналы и рабочие данные вручную.

Сохраняются три последних успешно применённых поколения, активное и
необходимые поколения отката со всеми используемыми ресурсами.
`cleanup` не требует запаса свободного диска и не создаёт файлов.
Незавершённая транзакция защищает оба поколения; восстановите её следующим
запуском обновления. Ограничения трафика и DNS описаны в
[README](../README.md#обновления-и-обслуживание).
