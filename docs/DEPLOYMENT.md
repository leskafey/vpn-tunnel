# Установка и обслуживание

Справочник по обслуживанию и нестандартной установке
[vpn-tunnel](https://github.com/leskafey/vpn-tunnel).
Серверные команды выполняются **от root** на Ubuntu 24.04 x86_64 в Bash/zsh.
Требования, основной сценарий установки, создание устройства и подключение
описаны в [README](../README.md). Локальные проверки кода и исторические
отчёты — в [DEVELOPMENT](DEVELOPMENT.md).

## Каталог установки

Рекомендуемый каталог — `/root/vpn-tunnel`. Установка использует каталог,
где находится `install-vpn.py`, независимо от текущего рабочего каталога.
Корень проекта должен принадлежать root и не быть доступен для записи
другим пользователям. `/root` и сам проект могут иметь закрытые права `0700`:
доступ служб обеспечивается отдельным пространством файлов systemd.
Права исходных родительских каталогов установщик не меняет.

Пробелы, кавычки, обратная косая черта, `$` и UTF-8 в пути поддерживаются.
Недопустимы `%`, перевод строки и возврат каретки. Полный абсолютный путь
корня проекта — не более **73 байт в UTF-8**. Ограничение связано с постоянным
Unix-сокетом `cache/backend/controller.sock`: его полный путь должен занимать
менее 104 байт, чтобы осталось место для завершающего NUL.
Путь проверяется до создания состояния установки и загрузки бинарников;
ошибка длины — `PROJECT_UNIX_SOCKET_PATH_TOO_LONG`. Выберите более короткий
каталог до первой установки. Пример допустимого пути:
`/srv/deployments/vpn-projects/vpn-tunel`.

Не перемещайте установленный проект: службы и сохранённые политики содержат
его абсолютный путь.

### Доступ DNS и HTTP к закрытому каталогу

DNS и HTTP продолжают работать от `vpn-policy`, с `ProtectSystem=strict`.
Для `/root/vpn-tunnel` в пространстве каждой службы создаются пустые tmpfs
только для чтения вместо `/root`, `/home`, `/run/user` и корня проекта.
Если есть другие закрытые родители, временные каталоги покрывают всю нужную
цепочку. Это отдельное представление файлов: настоящие права `/root` не
меняются, ACL для него не добавляются.

`BindReadOnlyPaths` подключает `lib/` и `data/` по прежним абсолютным путям.
DNS дополнительно видит `config/` и получает запись в `cache/backend/` через
`BindPaths` и `ReadWritePaths`. HTTP не получает доступа к конфигурациям и кэшу.
Подключаются каталоги, поэтому атомарная замена `backend.yaml` и публикация
новых поколений видны службам. `profiles/` и `state/` не подключаются;
ключи, реестр устройств и исходные личные правила в `config/` остаются `0600`.

В DNS/HTTP-юнитах `ProtectHome=no` сочетается с явными tmpfs для домашних
каталогов. Встроенные режимы `ProtectHome` перекрывают монтирование `/root`,
а `ProtectHome=tmpfs` задаёт ему `0700`, что препятствует проходу `vpn-policy`.
Защиту здесь обеспечивают явные временные каталоги и разрешённые bind-монтирования.
Корневые службы обновления сохраняют `ProtectHome=read-only` и свои точечные
`ReadWritePaths`; их доступ к приватным данным нужен для обслуживания.

Для путей с кавычками, обратной косой чертой, двоеточием или табуляцией
сохраняется обычная модель доступа по правам пользователя: в systemd 255
такие bind/tmpfs-пути могут изменяться при передаче исполняющему процессу.
В этом случае корень и родители должны разрешать проход `vpn-policy`.
Аудит проверяет фактический проход от существующего пользователя, включая
его группы и уже заданные ACL. Если пользователя ещё нет, нужен проход для
остальных пользователей, как в прежнем сценарии. Установщик не добавляет ACL
и не открывает закрытые родители для таких нестандартных путей.
Используйте рекомендованный путь без этих символов для установки под закрытым `/root`.

Аудит проверяет модель доступа, поддержку пространств монтирования и tmpfs,
а также `CAP_SYS_ADMIN` процесса установки. Он не меняет права, не создаёт
пользователей и не изменяет службы. Дополнительные пакеты для механизма доступа
не нужны; эти требования относятся и к установке одним `install-vpn.py`.
При установке и `--resume` служебные каталоги получают нужных владельцев,
группы и права перед запуском служб. Права проекта и его родителей сохраняются.
`vpn-policy` должен иметь отдельные ненулевые UID и GID.

### Служебные каталоги и права

Все пути в таблице указаны относительно корня проекта:

| Путь | Содержимое |
| --- | --- |
| `lib/`, `lib/bin/` | Установленный код и закреплённые бинарники |
| `config/` | Личные правила, настройки, конфигурации Xray и DNS, реестр устройств и приватные данные доступа |
| `profiles/` | Пользовательские SMART/FULL-профили; каталог `0700`, JSON `0600` |
| `data/generations/`, `data/current` | Проверенные серверные политики и небольшие клиентские JSON; `current` ссылается на активное поколение |
| `data/` | Блокировка обновлений и журналы восстановления |
| `cache/backend/` | Рабочий кэш Mihomo; владелец `vpn-policy`, права `0700` |
| `state/install/` | Журнал установки, контрольная точка ключей и временные загрузки |

Приватные конфигурации root имеют `0600`; необходимые DNS/HTTP файлы доступны
только root и группе `vpn-policy` (`0640`, каталоги `0750`). Личные правила и
профили не доступны HTTP-службе. Установленный код, конфигурации, профили,
ключи, кэш и рабочие данные исключены из Git.
Команда `/usr/local/sbin/vpnctl` и юниты `/etc/systemd/system/vpn-stack-*`
находятся в системных каталогах. Отдельного корня рабочих данных вне проекта нет.
DNS, SOCKS и HTTP правил слушают loopback.

Проверка политики использует короткий приватный временный сокет
`data/.s-XXXXXXXX/api.sock`, а её конфигурации и MRS остаются в поколении.
Каталог сокета имеет `0700` и удаляется после остановки проверочного процесса,
включая ошибки проверки.

## Установка без Git

В этом варианте Git не нужен; остальные [требования README](../README.md#требования)
сохраняются. Скопируйте один `install-vpn.py` в корень будущей установки,
например `/root/vpn-tunnel/`, с владельцем root и правами каталога `0700`
или `0755`.
Бинарники скачиваются отдельно и проверяются по закреплённым SHA-256.
Не запускайте файл из `/tmp` или чужого доступного для записи каталога.

```sh
python3 /root/vpn-tunnel/install-vpn.py audit
systemd-run --wait --pipe --collect --unit=vpn-stack-install \
  -p MemoryMax=768M -p MemorySwapMax=0 -p TasksMax=64 \
  -p RuntimeMaxSec=1800 -p UMask=0077 \
  /usr/bin/python3 /root/vpn-tunnel/install-vpn.py install --server-ip IP_НОВОГО_VPS
```

Укажите публичный IPv4 VPS вместо `IP_НОВОГО_VPS`. Эта команда задаёт те же
лимиты процесса установки, что и `install.sh`. Признак успеха —
`VPN_STACK_INSTALL_OK`. Установщик не меняет firewall; входящий TCP 443
должен быть открыт.
Итоговый отчёт показывает каталог профилей и полные пути файлов личных правил.

## Восстановление прерванной установки

Установка рассчитана на чистый VPS, в том числе после переустановки ОС.
Повторный запуск не перезаписывает существующую установку. После прерывания
устраните причину и добавьте `--resume` к исходной команде установки.
Сохраните версию установщика, каталог и публичный IP. Для `install.sh`
команда приведена в [README](../README.md#установка-на-vps); при установке
без Git добавьте `--resume` после IP в команде `systemd-run` выше.

Ключи и служебный UUID берутся из контрольной точки
`state/install/identity.json`; личные правила сохраняются без перезаписи.
Начальных пользовательских устройств нет. SMART/FULL для проверки создаются
временно и удаляются. Служебная учётная запись `probe` не выдаётся пользователю:
она остаётся в серверных конфигурациях и приватной конфигурации проверок.

Журнал `state/install/installation.json` хранит статус установки, IP и
контрольные суммы кода, бинарников, юнитов и приватных конфигураций. При
продолжении установщик сверяет сохранённое состояние и отказывается принимать
несовпадающий код или изменённые управляемые файлы. Личные правила сохраняются
отдельно и не требуют возврата к исходному содержимому.

Начальный журнал готовится в приватном временном каталоге
`.vpn-initialize-*/state/install/` внутри проекта. После записи и синхронизации
контрольной точки весь `state/` публикуется атомарно, без замены существующего
каталога. Прерывание до публикации не оставляет штатного `state/` без журнала:
`--resume` заново проходит проверки чистого сервера и начинает инициализацию.
Если публикация завершена, используется готовый журнал.

После аварийного завершения временный каталог подготовки может остаться.
Установщик не принимает его за состояние и не переносит из него файлы.
Чужие каталоги, приватные конфигурации или штатное состояние без журнала
не удаляются и не принимаются за собственную установку. Отсутствие журнала
при уже созданной идентичности приводит к отказу; существующие ключи и UUID
сохраняются.

## Обслуживание устройств

[Повседневные команды](../README.md#управление-устройствами) описаны в README.
Имя устройства — от 1 до 40 символов: первая буква `a`–`z`, далее строчные
латинские буквы, цифры или дефис. Имя `probe` зарезервировано.
Поддерживается до 256 пользовательских устройств.

`list` показывает только имена пользовательских устройств. Служебная учётная
запись проверок скрыта из списка и не имеет файлов в `profiles/`.
`export` выводит пути и восстанавливает отсутствующие JSON с прежним UUID.
Каталог `profiles/` должен существовать, принадлежать root, быть приватным
и не быть симлинком. Изменённые вручную JSON не перезаписываются: возвращается ошибка.

`revoke` отзывает доступ и локально проверяет отказ. Отсутствие каталога
профилей не препятствует отзыву. Неизменённые JSON удаляются, изменённые
сохраняются с сообщением; их UUID уже отозван.

Добавление и отзыв перезапускают Xray, соединения могут переподключиться.
Журнал `data/device-transaction.json` содержит данные для возврата конфигурации
Xray, реестра устройств и затронутых профилей. Незавершённая операция
откатывается перед следующей операцией с устройством или запуском Xray после
перезагрузки. После отката незавершённого отзыва повторите `revoke`.

## Правила и лимиты

Назначение файлов, команды и приоритеты правил описаны в
[README](../README.md#личные-правила).

Доменные файлы — UTF-8, одна запись на строку, без схемы, порта и пути.
Запись охватывает домен и поддомены, `#` начинает комментарий.
Общий предел каждого доменного файла — 64 КиБ, строки — 4096 байт;
PROXY и ads-exceptions — до 2048 уникальных доменов.
Личный DIRECT — до 256 доменов и 32 КиБ клиентского JSON.

Личные IP: UTF-8-комментарии, активные записи ASCII; публичные IPv4/CIDR,
маски `/12`–`/32`, у сетей нулевые биты хоста. Парсер Python `ipaddress`
проверяет `is_global` сети, первого и последнего адреса, отдельно запрещает
multicast. Это проверка свойств адресов, а не доступности или владельца сети.
До 256 входных записей до удаления дублей и 32 КиБ файла вместе с комментариями.
Итог вместе с автоматическими IP — до 256 свёрнутых CIDR и 32 КиБ JSON.
Удаление личного IP не удаляет такое же автоматическое правило.

Большие источники для личных правок заново не скачиваются. Невалидная правка
сохраняет рабочую политику. Задержки применения и интервалы доставки SMART
указаны в [README](../README.md#личные-правила) и
[разделе обновлений](../README.md#обновления-и-обслуживание).
На отключённом устройстве обновление возможно после подключения.
FULL клиентские списки IP и DIRECT не загружает.


## Диагностика и очистка

```sh
vpnctl status
vpnctl cleanup
journalctl -u vpn-stack-personal.service -n 30 --no-pager -o cat
journalctl -u vpn-stack-daily.service -n 60 --no-pager -o cat
journalctl -u vpn-stack-ip.service -n 60 --no-pager -o cat
```

Статус проверяет локальные Xray/DNS/HTTP, systemd-службы и таймеры,
целостность сохранённых конфигураций, незавершённые транзакции и неприменённые
личные правки. Наличие неприменённых правок отражается в отчёте и само по себе
не означает ненулевой код. Успешный неактивный oneshot нормален; штатный
отложенный запуск с кодом 75 не ухудшает статус. OOM, сигнал, тайм-аут и другие
ошибки служб дают `degraded` и код 1. Внешний вход, интернет и подключение
физического устройства проверяются отдельно.

Журнал `data/transaction.json` хранит состояние применения политики и данные
для отката. Следующий запуск обновления восстанавливает незавершённую
транзакцию. Не удаляйте журналы и рабочие данные вручную.

Сохраняются три последних успешно применённых поколения, активное и
необходимые поколения отката со всеми используемыми ресурсами.
`cleanup` не требует запаса свободного диска и не создаёт файлов.
Незавершённая транзакция защищает оба поколения; восстановите её следующим
запуском обновления. Ограничения трафика и DNS описаны в
[README](../README.md#обновления-и-обслуживание).
